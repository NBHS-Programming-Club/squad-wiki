The Programming Squad guide

This is the working manual for learning programming in the squad. Follow the sections in order if you are new. Each chapter explains what to learn, what to practise, how to check your understanding, and what evidence to keep in your repository.

Audience: complete beginners and returning studentsFormat: self-paced with mentor check-insTime: one school term or longer

1. Start here

You do not need to know how to code before beginning. You do need a computer, regular practice time, and a willingness to read error messages instead of hiding them.

How to use this guide: read the shared chapters once, choose one pathway, then work through its milestones in order. Do not skip the checkpoint just because the code runs; the checkpoint is where you explain why it works.

What you will produce

A personal notes file with new terms and questions.
Small exercises that demonstrate each foundation.
A GitHub repository with meaningful commits.
A final project another person can run.
A README explaining decisions and limitations.
A short demonstration and reflection.

First-week checklist

  1. Choose a regular schedule. Two focused sessions of 45–60 minutes are a better starting point than an occasional long session.
  2. Create a learning folder. Keep exercises separate from your final project so experiments do not damage finished work.
  3. Install the shared tools. Use the setup chapter and run the verification commands before starting a lesson.
  4. Make your first commit. It can contain only a README. The point is to practise the workflow early.
  5. Ask a precise question. Include what you expected, what happened, and the smallest code or error that shows the problem.

3. Shared foundations

These ideas appear in every pathway. Learn them through tiny programs rather than trying to memorise definitions. A concept is useful when you can use it, explain it, and fix it when it fails.

TopicLearn to doCheckpoint
Values and variablesStore text, numbers, and true/false values; choose clear names.Write a program that accepts input and prints a useful result.
ConditionsMake a decision with if, else, and comparisons.Handle valid, invalid, and boundary input.
Loops and collectionsRepeat work over lists, arrays, or objects.Process a small dataset without repeating code manually.
FunctionsGive a task a name, inputs, and a predictable output.Test a function with normal and unusual inputs.
Files and dataRead, write, parse, and validate data.Explain what happens when a file is missing or malformed.
DebuggingReduce a problem, inspect values, and change one thing at a time.Write a short bug report and its fix.
TestingCheck expected behaviour automatically and manually.Keep a regression test for every bug you fix.

Learning workflow

For each lesson, read a small amount, predict what the code will do, run it, change one part, and explain the result in your notes. If you are stuck for more than 20 minutes, make the problem smaller or ask for help with evidence.

Git and GitHub

Use commits as checkpoints, not as a backup of every keystroke. A good commit says what changed: Add input validation for score parser. Push after a working checkpoint and review the diff before sharing it.

git status
git add .
git commit -m "Add first exercise"
git log --oneline
git push

4. Choose a pathway

Choose the kind of problems you want to spend time with. You can explore all four descriptions, but follow one roadmap for a complete term so that your final project has enough depth.

ML & AI · Python, data, and evaluation

Choose this pathway if you want to investigate patterns in data and are willing to learn some statistics. The important skill is not making a model produce an answer; it is measuring when the answer is unreliable.

1. PythonTypes, functions, modules, files, exceptions, and virtual environments.
2. DataCSV files, cleaning, tables, plots, distributions, and honest summaries.
3. ModelsFeatures, labels, train/test split, baselines, regression, and classification.
4. ResponsibilityBias, privacy, leakage, uncertainty, reproducibility, and limitations.

Practice sequence

  1. Analyse a small dataset and write three supported observations.
  2. Build a simple baseline before using a more complex model.
  3. Compare results with a metric that matches the question.
  4. Make a reproducible script and a report another person can follow.

Game development · Godot, systems, and design

Choose this pathway if you like interactive systems and feedback. A small finished game teaches more than an ambitious game that cannot be played.

1. Editor and scenesNodes, scenes, scripts, signals, input actions, and the game loop.
2. Core mechanicsMovement, collision, state, goals, failure, restart, and camera control.
3. Player experienceLevels, difficulty, UI, sound, animation, feedback, and accessibility.
4. ReleasePlaytesting, bug triage, export builds, credits, and a postmortem.

Practice sequence

  1. Make a character move in one room.
  2. Add one challenge, one goal, and a reliable restart.
  3. Playtest with three people and record what they actually do.
  4. Cut features until the remaining game is polished and explainable.

Informatics · algorithms and problem solving

Choose this pathway if you enjoy turning a problem into a precise algorithm. You will practise proving why a solution works and estimating its time and memory use.

1. Core C++Input, output, functions, vectors, strings, sorting, and debugging.
2. PatternsPrefix sums, two pointers, binary search, greedy methods, and recursion.
3. StructuresStacks, queues, maps, trees, graphs, heaps, and disjoint sets.
4. StrategyDynamic programming, shortest paths, range queries, proofs, and contest review.

Practice sequence

  1. Read the constraints before writing code.
  2. Write a brute-force solution or examples to expose the pattern.
  3. State the algorithm and complexity in plain language.
  4. After a contest, revisit every miss and write the lesson learned.

Web development · interfaces, data, and services

Choose this pathway if you want to build tools that people use in a browser. Start with accessible HTML, then add behaviour, persistence, and a backend only when the problem needs it.

1. Frontend basicsSemantic HTML, CSS layout, responsive design, forms, and accessibility.
2. JavaScriptEvents, DOM state, modules, asynchronous requests, loading, and errors.
3. ApplicationsComponents, routing, typed data, validation, tests, and a clear UI model.
4. Full stackHTTP, SQL, authentication, authorisation, deployment, logging, and recovery.

Practice sequence

  1. Build a semantic page that works without JavaScript.
  2. Add one interaction with visible loading, empty, and error states.
  3. Model the data before writing the API.
  4. Test keyboard use, mobile layout, validation, and deployment from a fresh clone.

5. Build the final project

The capstone is the end of the guide, not the first activity. It should answer a real question, solve a defined problem, or create a complete experience for a specific user. The project is assessed by its reasoning and documentation as well as its output.

5.1 Plan before coding

Write a one-page proposal. Name the user, the problem, the smallest useful result, and what you will deliberately not build. List unknowns as questions to investigate.

Planning deliverable: proposal, user story or problem statement, sketch, scope cut list, risks, and a definition of “done”.

5.2 Set up a maintainable repository

Start with a README, a sensible folder structure, an ignored secrets file, and a way to run the project from a fresh clone. Make the first commit before adding features.

README.md
src/              # source code
tests/            # automated checks, when applicable
assets/           # small, redistributable assets
.gitignore

5.3 Implement in vertical slices

Build one small path from input to useful output. Keep it runnable, then add the next slice. Commit after each verified behaviour. Avoid building an entire layer before checking that the user journey works.

SliceEvidence
Happy pathA new user can complete the main action.
Invalid inputThe project explains what is wrong and does not corrupt state.
Empty or missing dataThe interface or program remains understandable.
Failure and recoveryYou can reproduce an error and explain how to recover.

5.4 Review, polish, and ship

Ask at least one other student to use the project without coaching. Watch rather than immediately explaining. Turn observations into issues, fix the highest-impact problems, and record trade-offs you kept.

A clean clone can be installed and run.
The README includes usage and known limits.
Core behaviour has tests or repeatable checks.
No secrets or private data are committed.
The project works at its intended screen size or target platform.
A demo explains the problem, design, result, and next step.

Final submission checklist

  1. Repository. Source, assets, setup instructions, and a meaningful commit history.
  2. Technical explanation. Architecture, important decisions, alternatives considered, and limitations.
  3. Verification. Tests, manual checks, screenshots or a playable build, and known issues.
  4. Demonstration. A short walkthrough that begins with the user problem, not a list of technologies.
  5. Reflection. What changed after feedback, what failed, and what you would do next.

6. Troubleshooting

Most errors are useful reports from a tool. Slow down, make the failure repeatable, and change one variable at a time.

“Command not found” or the editor cannot find a tool

Confirm the tool is installed, restart the terminal, and check its version. On Windows, verify the installer added the tool to PATH. On macOS or Linux, check the shell configuration. Record the exact command and operating system before asking for help.

The program runs but gives the wrong answer

Write the smallest input that demonstrates the wrong result. Print or inspect intermediate values. Compare the program with a hand-worked example, then add that example as a test so the bug does not return.

Git says there are conflicts or rejected changes

Do not delete files to make the message disappear. Read git status, inspect the conflicting sections, keep the intended content, then test before committing. Ask a mentor if you are unsure which version is correct.

I copied a tutorial and do not understand my own project

Stop adding features. Rename variables, explain each function in your notes, and rebuild one small part without looking. The goal is transferable understanding, not a particular code listing.

I am stuck and do not know what to ask

Use this format: “I am trying to ___. I expected ___. Instead I got ___. I tested ___. Here is the smallest relevant code/error: ___.” This gives another person enough context to help without guessing.

7. Glossary and next steps

TermMeaning in this guide
AlgorithmA precise sequence of steps for solving a class of problems.
APIA defined way for one program or service to request data or actions from another.
BugObserved behaviour that does not match the intended behaviour.
CommitA named, recorded change in a Git repository.
DependencyCode or software your project relies on to run.
IterationA small cycle of building, checking, learning, and improving.
RepositoryA project folder tracked by Git, often shared through GitHub.
ScopeThe boundary of what a project will and will not include.
After the capstone: publish a short retrospective, choose one next technical topic, and improve the project in a small follow-up issue. A finished project is a foundation for the next one, not a final test of whether you belong.
